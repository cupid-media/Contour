# RabbitMQ-транспорт 

## Из чего состоит

```
RabbitBus
├── ConnectionPool               — соединения с брокерами, общие для получателей и отправителей
├── RabbitReceiver               — один на входящую метку (incoming)
│   └── RabbitReceivingSource × число адресов в строке подключения
│       └── канал + консьюмер × ParallelismLevel
└── RabbitSender                 — один на исходящую метку (outgoing)
    └── RabbitProducer × число адресов в строке подключения
        └── общий канал отправки соединения
```

Под капотом стоит RabbitMQ.Client 7. Его автовосстановление соединений выключено: восстановлением
занимается сам Contour (см. «Обрывы и восстановление»).

### Несколько брокеров

Строка подключения может содержать несколько адресов через запятую:
`amqp://a:5672/vhost,amqp://b:5672/vhost`. Это не кластер, а независимые брокеры:

- получатель слушает очередь **на каждом** из них;
- отправитель держит продюсер на каждом и отправляет по очереди на исправные (round-robin).

## Топология

Contour сам объявляет точки обмена и очереди при подготовке шины. Всё создаётся durable.

```
отправитель                    брокер                                   получатель
EmitAsync("user.created") ──▶ exchange user.created (fanout)
                                 ├──▶ queue ServiceA.user.created ──▶ ServiceA
                                 └──▶ queue ServiceB.user.created ──▶ ServiceB
```

- **Точка обмена** называется меткой сообщения и имеет тип fanout: сообщение уходит во все
  привязанные очереди, ключ маршрутизации пустой и не используется. Поэтому `PublishingOptions.Key`
  RabbitMQ не поддерживает и пишет предупреждение в лог.
- **Очередь** у каждого сервиса своя: `<endpoint>.<метка>`. Так каждый подписчик получает свою копию
  события, а экземпляры одного сервиса делят сообщения своей очереди между собой.
- **Отложенная доставка.** Для маршрута с `Delayed()` точка обмена создаётся типа
  `x-delayed-message` (нужен плагин брокера), а задержка берётся из `PublishingOptions.Delay`.
- **Метка** сообщения дополнительно передаётся в заголовке `x-message-type`.
- **Маршрут на любую метку** (`Route(MessageLabel.Any)`) объявляет точку обмена лениво, при первой
  отправке с новой меткой.

## Получение

### Каналы и параллельность

На каждый адрес брокера получатель открывает `ParallelismLevel` каналов (по умолчанию 1) и на
каждом запускает консьюмер очереди. Каналы по умолчанию живут на одном соединении из пула
(`ReuseConnection`).

RabbitMQ.Client выдаёт сообщения одного канала **строго по одному**: следующее приходит в
обработчик, только когда завершился `HandleAsync` предыдущего. Значит, одновременно обрабатывается
до `ParallelismLevel × число брокеров` сообщений на одну метку.

### Предвыборка (QoS)

Брокер не ждёт, пока обработчик попросит следующее сообщение, а заранее отправляет клиенту до
`prefetchCount` неподтверждённых сообщений на канал, по умолчанию 50 (`WithQoS`). Они лежат в
буфере клиента и ждут своей очереди. Предвыборка работает только с ручным подтверждением, то есть
с `RequiresAccept()`.

### Подтверждение

Это главное отличие режимов получателя:

| | Без `RequiresAccept()` (по умолчанию) | С `RequiresAccept()` |
|---|---|---|
| Когда брокер удаляет сообщение | сразу при отправке клиенту (auto-ack) | после `AcceptAsync` или `RejectAsync` |
| `AcceptAsync`, `RejectAsync` | ничего не делают | `basic.ack` / `basic.nack` |
| Предвыборка `QoS` | не действует | ограничивает число неподтверждённых |
| Сервис упал посреди обработки | сообщение потеряно | вернётся в очередь и придёт снова |

С `RequiresAccept()` сообщение, которое так и не подтвердили, остаётся за каналом, пока тот открыт,
и возвращается в очередь, когда канал закроется. Доставка тогда **как минимум один раз**,
обработчики должны быть идемпотентными.

`RejectAsync(requeue: true)` сразу возвращает сообщение в очередь, и оно придёт снова, возможно
другому экземпляру. `RejectAsync(requeue: false)` удаляет его.

### Обработка одного сообщения

1. Если у сообщения есть `CorrelationId`, но нет адреса ответа, это ответ на запрос: оно
   отдаётся ожидающему `RequestAsync` (см. «Запрос-ответ»).
2. Иначе заголовки сообщения запоминаются, чтобы `x-correlation-id` и `x-breadcrumbs` перешли в
   сообщения, которые обработчик отправит по ходу, и вызывается `HandleAsync`.
3. Обработчика нет — работает стратегия необработанных сообщений (`OnUnhandled`).
4. Обработчик бросил исключение — работает стратегия провалов (`OnFailed`).

### Провалы и fault-очередь

Стандартная стратегия перекладывает и упавшее, и необработанное сообщение в fault-очередь, а
исходное подтверждает. Она включается `UseDefaultFaultStrategy()`; при настройке шины из секции
конфигурации — всегда.

- точка обмена `<endpoint>.Fault` (topic) и очередь с тем же именем, общие для обоих случаев;
- в очередь кладётся `FaultMessage`: исходный payload, заголовки, время получения и исключение;
- сообщения живут в ней `FaultQueueTtl` (по умолчанию 21 день), длину можно ограничить
  `FaultQueueLimit`.

Без стратегии упавшее сообщение просто логируется. Тогда с `RequiresAccept()` оно остаётся
неподтверждённым до закрытия канала, а без него уже удалено брокером.

Базовые консьюмеры Gems.ServiceBus.Emitting ловят исключение сами: делают `RejectAsync(false)` и
пересылают сообщение в `document.contour.failed`.

## Батчевые обработчики

Батчевый обработчик (`BaseBatchNoReplyingConsumer<T>` из Gems.ServiceBus.Emitting) складывает
сообщение в пачку и сразу возвращает управление из `HandleAsync`. Канал тут же выдаёт ему
следующее. Пачка обрабатывается, когда наберётся лимит или сработает таймер, и после этого каждое
сообщение пачки получает `AcceptAsync`.

```
канал:   m1 → m2 → … → m50   (каждое сразу «обработано», ждёт Accept)
пачка:   [m1 … m50] ──── обработка ────▶ ack × 50
```

Что из этого следует:

- **Нужен `RequiresAccept()`.** Без него брокер удалил сообщения ещё при доставке, и падение
  сервиса до обработки пачки их теряет.
- **Пачка ограничена предвыборкой.** Неподтверждённых на канале не бывает больше `prefetchCount`:
  получив 50 сообщений, брокер ждёт подтверждений. Если лимит пачки больше `prefetchCount ×
  ParallelismLevel`, он не наберётся никогда, и пачка будет уходить только по таймеру.
- Отдельного механизма противодавления, как в Kafka, не нужно: его роль играет предвыборка.

## Обрывы и восстановление

- **Соединение.** Если не удалось подключиться, Contour повторяет попытку с паузой 0, 1, 2 … до
  10 с, бесконечно.
- **Канал получателя закрылся не по нашей инициативе** (обрыв соединения, ошибка протокола).
  Источник получения пересоздаёт каналы и консьюмеров заново, повторяя раз в секунду, пока не
  получится. Неподтверждённые сообщения брокер к этому моменту уже вернул в очередь.
- **Канал продюсера закрылся.** Продюсер пересоздаётся так же, раз в секунду. Пока он не готов,
  отправка уходит на другие брокеры из строки подключения, если они есть.
- **Брокер заблокировал соединение** (кончается память или диск). Продюсеры этого соединения
  считаются неисправными, и round-robin их пропускает.

## Отправка

### Продюсер

На каждый адрес брокера у отправителя один продюсер. Все продюсеры одного соединения публикуют
через **один общий канал** (отдельный для маршрутов с подтверждением), и операции на нём
выполняются по одной. Отдельной буферизации и
батчинга, как у librdkafka, здесь нет: каждое сообщение — отдельный `basic.publish`.

При отправке из `PublishingOptions` и настроек маршрута собираются свойства AMQP:

| Опция | Что делает |
|---|---|
| `Persistently` | `delivery-mode = persistent`: брокер пишет сообщение на диск |
| `Ttl` | `expiration`: брокер удалит сообщение, если его не забрали вовремя |
| `Delay` | заголовок `x-delay` для `x-delayed-message`; без `Delayed()` у маршрута игнорируется с предупреждением |
| `Key` | не поддерживается: точки обмена fanout; игнорируется с предупреждением |
| `AdditionalHeaders` | заголовки сообщения |

### Подтверждение публикации

- **Без подтверждения** (по умолчанию) `EmitAsync` завершается, когда сообщение записано в сокет.
  Если брокер в этот момент упадёт, сообщение пропадёт, и отправитель об этом не узнает.
- **С `WithConfirmation()`** канал переводится в режим publisher confirms. `EmitAsync` ждёт `ack`
  брокера на это сообщение. `nack` превращается в `MessageRejectedException`, отсутствие ответа за
  `ConfirmationTimeout` — в `UnconfirmedMessageException`.

### Повторы

Сорвавшаяся отправка повторяется до `FailoverAttempts` раз (по умолчанию 7), каждый раз на
следующем исправном продюсере. Если исправных нет, берётся любой. Когда попытки кончились,
`EmitAsync` бросает `FailoverException` со всеми ошибками внутри.

`ForwardAsync` и ответы из обработчика уходят через то же соединение, с которого пришло исходное
сообщение. Исключение — fault- и unhandled-очереди: туда отправка идёт через любой брокер.

## Запрос-ответ

- У маршрута с `WithDefaultCallbackEndpoint()` каждый продюсер заводит **свою временную очередь
  ответов**: `<endpoint>.replies-<метка>-<случайное>`, exclusive и auto-delete. Брокер удалит её,
  когда закроется соединение.
- Запрос уходит с `reply-to` на эту очередь и `correlation-id`.
- Обработчик отвечает через `ReplyAsync`: ответ публикуется в стандартную точку обмена прямо в
  очередь запросившего, с тем же `correlation-id`.
- Ответ, пришедший позже таймаута (`RequestTimeout`, по умолчанию 30 с), никто не ждёт: он
  считается необработанным, а `RequestAsync` к тому времени уже завершился с `TimeoutException`.
- Если очередь ответов пропала вместе с каналом, продюсер пересоздаётся с новой очередью, а
  ожидающие запросы отменяются.

## Остановка

1. **Чтение.** Консьюмеры отписываются от очередей (`basic.cancel`), новые сообщения больше не
   приходят. Сообщения, которые уже лежат в буфере клиента, обработчику не отдаются. С
   `RequiresAccept()` они вернутся в очередь при закрытии канала; без него они потеряны: брокер
   уже считает их доставленными.
2. **Обработчик освобождается**, если он `IAsyncDisposable` и зарегистрирован напрямую, а не через
   ленивую обёртку. Батчевый обработчик при этом дообрабатывает накопленную пачку; каналы ещё
   открыты, поэтому её `AcceptAsync` доходят до брокера. Иначе неподтверждённая пачка вернётся
   в очередь на шаге 5.
3. **Сообщения в обработке.** Шина ждёт, пока завершатся все уже начатые `HandleAsync`.
4. **Отправка.** Останавливаются продюсеры и их очереди ответов. Ожидающие `RequestAsync`
   отменяются.
5. **Соединения** закрываются, когда шину освобождают. Всё, что осталось неподтверждённым, брокер
   вернёт в очередь.
