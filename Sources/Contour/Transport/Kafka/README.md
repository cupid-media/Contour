# Kafka-транспорт 

## Из чего состоит

```
KafkaBus
├── KafkaReceiver               — один на топик, на который подписан обработчик
│   └── KafkaReceivingSource    — превращает сообщения Kafka в вызовы IConsumerOf<T>
│       └── KafkaConsumer × ParallelismLevel
│           └── KafkaConsumeLoop   — цикл чтения на выделенном потоке
│               ├── PartitionOffsetTracker   — какие оффсеты можно коммитить
│               └── DeferredAcknowledgements — подтверждения, которые придут позже
└── KafkaSender                 — один на маршрут отправки
    └── KafkaProducer           — обёртка над одним Confluent-продюсером
```

Под капотом стоит Confluent.Kafka, то есть librdkafka. Всё, что она делает сама (поиск лидеров
партиций, ребалансы, буферизация и батчинг на отправке), транспорт не дублирует.

## Чтение

### Воркеры

У каждого топика имеется `ParallelismLevel` воркеров (по умолчанию один). Воркер — это отдельный
Confluent-консьюмер в общей consumer group, поэтому Kafka делит партиции топика между воркерами
всех экземпляров сервиса. Воркеров больше, чем партиций, делать бессмысленно: лишние простаивают.

Каждый воркер работает на своём выделенном потоке: `Consume` в librdkafka блокирующий, и в пуле
потоков ему не место.

### Цикл

Один виток цикла:

```
┌────────────────────────────────────────────────────────────────┐
│ 1. Backpressure: слишком много неподтверждённых — пауза        │
│ 2. Consume(200 мс)                                             │
│      ошибка   → пауза 200 мс … 5 с, снова на 1                 │
│      пусто    → checkpoint (коммит по таймеру), снова на 1     │
│      сообщение↓                                                │
│ 3. Трекер: оффсет «получен, не подтверждён»                    │
│ 4. Обработчик: await HandleAsync                               │
│      решение уже есть → подтвердить или удержать оффсет        │
│      решения ещё нет  → в отложенные, читать дальше            │
│ 5. Checkpoint: учесть пришедшие отложенные, коммит, если пора  │
└────────────────────────────────────────────────────────────────┘
```

Главное свойство: **воркер передаёт обработчику по одному сообщению** и не читает следующее, пока
не завершится `HandleAsync` предыдущего. Так сохраняется порядок внутри партиции. Параллельность
даёт число воркеров, а не перекрывающиеся вызовы обработчика.

Consume ограничен 200 мс, а не ждёт сообщения бесконечно. Иначе на тихом топике воркер не
просыпался бы, не коммитил хвост по таймеру и не замечал бы остановку.

Если Consume падает (брокер недоступен, нет прав), воркер ждёт 200 мс, потом 400 мс и так далее
до 5 с. Без паузы такая ошибка возвращается мгновенно, и цикл занял бы ядро и залил лог. Остановку
воркер замечает и во время паузы.

### Обработка одного сообщения

`KafkaReceivingSource` превращает сообщение в `IConsumingContext<T>` и вызывает обработчик.
Десериализация происходит уже внутри обработки: битый payload — такой же провал обработки, как
исключение в обработчике, и разбирает его та же стратегия.

Обработка возвращает **два результата в разное время**:

1. «Обработчик вернул управление» — когда завершился `HandleAsync`. Этого ждёт воркер, прежде чем
   читать дальше.
2. «Решение по оффсету» — продвигать его (`true`) или удержать (`false`). Обычно оно известно сразу,
   но может прийти позже (см. «Батчевые обработчики»).

Решение принимается так:

| Что сделал обработчик | Решение |
|---|---|
| `AcceptAsync()` | продвинуть |
| `RejectAsync(requeue: false)` | продвинуть: сообщение пропущено |
| `RejectAsync(requeue: true)` | удержать: прочитается снова после рестарта или ребаланса |
| Ничего, маршрут без `RequiresAccept()` | продвинуть |
| Ничего, маршрут с `RequiresAccept()` | ждать `AcceptAsync`/`RejectAsync`, которые придут позже |
| Бросил исключение, стратегии нет | продвинуть, с ошибкой в логе |
| Бросил исключение, стратегия есть | что решит стратегия; по умолчанию продвинуть |

Стратегия провалов (`OnFailed`, `UseDefaultFaultStrategy`) — аналог fault-очереди RabbitMQ:
упавшее сообщение перекладывается в fault-топик `<endpoint>.fault`. Как и fault-очередь RabbitMQ,
fault-топик пишется через свой маршрут с настройками отправки уровня шины (`WithConnectionString`,
SSL), а не в кластер, из которого прочитано сообщение: все упавшие сообщения конечной точки
собираются в одном месте. Без адреса кластера на уровне шины `UseDefaultFaultStrategy` не
сконфигурируется. Маршрут можно объявить и явно через `Route("<endpoint>.fault")`, тогда берутся
его настройки. Если упала сама стратегия,
оффсет удерживается. В Kafka нельзя вернуть одно сообщение в очередь, и пропустить его значило бы
потерять навсегда.

### Какой оффсет коммитится

Коммитится не «последний обработанный + 1», а **наименьший полученный, но ещё не подтверждённый**
оффсет. Это делает `PartitionOffsetTracker`, отдельно для каждой партиции.

```
партиция 3:  100 ✔  101 ✔  102 …  103 ✔  104 ✔
                           ▲
                коммит = 102: 103 и 104 обработаны, но 102 ещё нет
```

Неподтверждённое сообщение держит позицию, и коммит не проскакивает его, даже если всё после него
уже обработано. При рестарте 102, 103 и 104 прочитаются снова: доставка **как минимум один раз**,
обработчики должны быть идемпотентными.

Учитываются только реально полученные оффсеты, поэтому пропуски в нумерации (компактированные и
транзакционные топики) не мешают.

### Когда коммитится

Коммит дорогой, поэтому не на каждое сообщение. Воркер коммитит, если с прошлого коммита:

- обработано `CommitOffset` сообщений, по умолчанию 1000;
- или прошло `CommitTimeout`, по умолчанию 5 с, и обработано хоть одно.

Обработанным считается сообщение, по которому есть решение, в том числе «удержать».

Проверка идёт после каждого сообщения и на каждом пустом poll, поэтому хвост тихого топика
закоммитится не позже чем через `CommitTimeout`. Если коммит сорвался, позиции не считаются
зафиксированными и уйдут в следующем коммите.

Ещё коммит выполняется принудительно при остановке и при отзыве партиций на ребалансе: обработанный
хвост не должен достаться новому владельцу партиции повторно.

С `EnableAutoCommit = true` транспорт не коммитит сам, а передаёт безопасные позиции клиенту
(`StoreOffset`), и librdkafka коммитит их по своему таймеру. Автосохранение оффсетов при этом
выключается: иначе клиент закоммитил бы оффсет полученного, но ещё не обработанного сообщения.

## Батчевые обработчики

Батчевый обработчик (`BaseBatchNoReplyingConsumer<T>` из Gems.ServiceBus.Emitting) не обрабатывает
сообщение в `HandleAsync`, а складывает его в пачку и сразу возвращает управление. Пачка
обрабатывается целиком, когда наберётся лимит или сработает таймер, и только после этого каждое
сообщение пачки получает `AcceptAsync`.

Чтобы это работало, у маршрута должен быть `RequiresAccept()`. Тогда:

1. `HandleAsync` вернулся, а решения по оффсету нет. Воркер **не ждёт** его: сообщение уходит в
   `DeferredAcknowledgements`, а воркер читает следующее и отдаёт его в ту же пачку.
2. Пачка обработана, обработчик вызывает `AcceptAsync` для её сообщений. Решения приходят с потока
   обработчика, а трекер принадлежит воркеру, поэтому они складываются в очередь.
3. На ближайшем checkpoint воркер забирает подтверждённые из очереди, отмечает их в трекере, и
   позиция коммита сдвигается.

```
воркер:     m1 → m2 → m3 → … → m50 → m51 → m52 …     (читает, не дожидаясь решений)
пачка:      [m1 … m50] ──── обработка ────▶ Accept × 50
трекер:     коммит стоит на m1 ───────────────────────▶ коммит сдвигается на m51
```

Пока пачка не подтверждена, коммит стоит на её первом сообщении. Если сервис упадёт до
подтверждения, вся пачка прочитается заново.

### Backpressure

Если обработчик не успевает за потоком, отложенные подтверждения копятся, а с ними и сообщения в
памяти. Когда их становится `MaxPendingAcknowledgements` (по умолчанию 10 000), воркер ставит
партиции на паузу (`Pause`) и продолжает делать poll, но уже по 20 мс и без новых сообщений.
Пауза снимается, как только число ожидающих падает ниже лимита.

Poll во время паузы не прекращается: иначе Kafka исключила бы воркер из группы по
`max.poll.interval.ms`, и он не увидел бы ребаланс. Паузу воркер ставит заново на каждом витке,
потому что партиции, назначенные ребалансом, приходят неприостановленными.

### Подтверждение после ребаланса

Если партицию отозвали, пока её пачка обрабатывалась, позднее подтверждение для неё ничего не
закоммитит: позиции отозванной партиции уже забыты. Новый владелец прочитает эти сообщения снова.

## Остановка

Остановка шины идёт по шагам:

1. **Чтение.** Каждому воркеру сигналят остановку. Текущий `HandleAsync` дорабатывает до конца,
   новых сообщений воркер не берёт.
2. **Отложенные решения.** Ещё не пришедшие подтверждения закрываются как «удержать»: шина не ждёт
   пачку, которая может обрабатываться сколько угодно. Пришедшие учитываются.
3. **Финальный коммит** всего подтверждённого, затем `Close` консьюмера. Без `Close` брокер ждал бы
   session timeout, прежде чем отдать партиции другим экземплярам.
4. **Сообщения в обработке.** Шина ждёт, пока завершатся все `HandleAsync`. В Kafka к этому
   моменту их уже нет: воркеры дождались их на шаге 1.
5. **Отправка.** Каждый продюсер делает `Flush`, до `FlushTimeout` (по умолчанию 10 с): без этого
   сообщения, ещё лежащие в буфере librdkafka, потерялись бы.

Не подтверждённые к остановке сообщения прочитаются после рестарта.

## Отправка

### Продюсер

На маршрут отправки приходится один Confluent-продюсер. Сообщение уходит через
`Produce(сообщение, колбэк)`:

- **Батчинг делает librdkafka.** Сообщения копятся в буфере и уходят брокеру пачками; `WithLinger`
  задаёт, сколько ждать наполнения пачки. Транспорт свою пачку не собирает.
- **С подтверждением** (`WithConfirmation`, по умолчанию включено) `EmitAsync` завершается, когда
  пришёл отчёт о доставке от брокера. Используется колбэк, а не `ProduceAsync`: отправка не ждёт
  каждое сообщение отдельно, и батчинг librdkafka сохраняется.
- **Без подтверждения** `EmitAsync` завершается, как только сообщение попало в буфер.

### Ключ сообщения

`PublishingOptions.Key` уходит ключом сообщения Kafka. Сообщения с одним ключом попадают в одну
партицию и читаются в порядке отправки. Без ключа партицию выбирает librdkafka.

Заданные опции, которые Kafka не поддерживает (`Ttl`, `Persistently`, `Delay`), пишут в лог
предупреждение, один раз на маршрут.

### Ошибки отправки

- **Сорвалась доставка** (таймаут, брокер отказал). Отправка повторяется до `FailoverAttempts` раз,
  по умолчанию 3, потом `EmitAsync` бросает `FailoverException`. Ключ при повторах сохраняется.
- **Фатальная ошибка продюсера.** librdkafka помечает такой продюсер окончательно сломанным.
  Транспорт пересоздаёт его перед следующей отправкой, а до тех пор маршрут считается нездоровым в
  health-check.

## Запрос-ответ

В Kafka нет временной очереди на одного клиента, как в RabbitMQ, поэтому `RequestAsync` устроен
так:

- У маршрута с ответом есть топик ответов. Запрос несёт его имя в `x-reply-route` и
  `x-correlation-id`.
- Каждый экземпляр шины слушает топик ответов **своей одноразовой группой** (`<endpoint>.reply.<guid>`)
  с позиции «только новые». Оффсеты этой группы не коммитятся.
- Ответы видят все экземпляры, но каждый берёт только те, чей `x-correlation-id` ждёт сам,
  остальные молча пропускает: это штатный трафик.
- Сообщение без `x-correlation-id` в топике ответов ответом не считается и уходит в стратегию
  необработанных (`OnUnhandled` на шине), а без неё пропускается с предупреждением в логе.

Отвечающий получатель объявляется с `WithReplies()`. Для кластера, который он читает, шина держит
продюсер, и ответ уходит в тот же кластер, откуда пришёл запрос: там топик ответов запросившего.
Пересылки (`ForwardAsync`) идут так же. Получателю со своей стратегией провалов (`OnFailed`)
продюсер заводится и без `WithReplies()`, потому что стратегия пересылает упавшие сообщения.
Адрес и SSL у продюсера берутся от получателя, остальные настройки отправки — уровня шины.
Стратегия по умолчанию (`UseDefaultFaultStrategy`) этого продюсера не требует: fault-топик
пишется в кластер шины.

Ответ живёт, только пока жив запросивший: после рестарта у экземпляра новая группа, и старые ответы
он не увидит. Для работы, которая должна пережить рестарт, используйте односторонние сообщения.

## Здоровье

Шина нездорова в health-check, если:

- любой воркер завершился во время чтения, то есть цикл упал с фатальной ошибкой;
- у любого маршрута отправки продюсер получил фатальную ошибку и ещё не пересоздан.
